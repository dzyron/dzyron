Phân tích thiết kế — Conway-Research/automaton

Runtime agent AI “tự chủ”: tự trả tiền compute bằng USDC, tự sửa code, tự nhân bản. Phân tích dựa trên source tại commit d8f8168 (26/08/2026), package @conway/automaton v0.2.1.

TL;DR. Automaton là một monolith Node.js/TypeScript chạy 1 tiến trình dài hạn, xoay quanh vòng lặp ReAct (think → act → observe) cộng một heartbeat daemon chạy nền. Toàn bộ trạng thái nằm trong một file SQLite (~/.automaton/state.db). Ý tưởng thiết kế trung tâm là “áp lực sinh tồn”: số dư credit quyết định survival tier → tier quyết định model được dùng, tần suất heartbeat, và cuối cùng là “chết”.

An toàn được xây theo kiểu defense-in-depth trong cùng tiến trình: constitution bất biến → policy engine chặn mọi tool call → injection defense → path protection → giới hạn tài chính → phân cấp authority. Thiết kế này hợp lý về ý tưởng, nhưng điểm yếu cốt lõi là agent chạy cùng tiến trình và có quyền sửa chính source code chứa các rào chắn đó.

Code đang ở giai đoạn phát triển nhanh: tài liệu kiến trúc đã lệch khá xa so với code (57 vs ~77 tool, schema v8 vs v11), có hai stack inference song song, và vài module lớn (compression engine, enhanced retriever) được viết + test nhưng chưa nối vào runtime.

1. Kiến trúc tổng thể

Không có service tách rời — mọi subsystem là module TS trong cùng một process, giao tiếp qua gọi hàm trực tiếp và qua bảng SQLite (vd. wake_events là “message bus” giữa heartbeat và agent loop). Bên ngoài chỉ có 3 phụ thuộc hạ tầng: Conway Cloud (VM, inference, domain, credits), social relay, và chain Base (USDC, ERC-8004).

2. Vòng đời runtime

index.ts bootstrap tuần tự (config → wallet → DB migrate → Conway/inference/social client → policy engine → spend tracker → bootstrap topup $5 → heartbeat) rồi vào vòng while(true) luân phiên giữa chạy agent loop và ngủ. Khi ngủ, cứ 30s nó “consume” một bản ghi trong bảng wake_events; heartbeat là bên ghi vào bảng này.

3. Agent loop (ReAct)

Mỗi turn trong agent/loop.ts:

1. Kiểm tra tài chính → tính survival tier (cache số dư trong KV khi API lỗi)
2. Claim tin nhắn inbox (received → in_progress, retry tối đa 3) + sanitize qua injection-defense
3. Build system prompt nhiều lớp (constitution, identity, soul, tài chính, skills, tools)
4. MemoryRetriever lấy memory trong token budget → chèn block memory
5. (nếu có bảng goals) orchestrator.tick() + chèn TODO.md vào context
6. InferenceRouter.route(tier, taskType) → gọi model
7. Thực thi tối đa 10 tool call/turn, mỗi call qua PolicyEngine
8. Persist turn (atomic cùng ack inbox) → MemoryIngestionPipeline
9. Phát hiện loop (cùng pattern tool 3 lần) → chèn cảnh báo hệ thống
10. Phát hiện idle (10 turn không có tool "mutating") → ép sleep; 5 lỗi liên tiếp → sleep

Lưu ý: ARCHITECTURE.md nói ngưỡng idle là 3 turn; code hiện tại là MAX_IDLE_TURNS = 10 và thêm giới hạn maxTurnsPerCycle (mặc định 25).

Nhận xét thiết kế: các guard chống “agent tự chạy vòng vòng tốn tiền” (loop detector, idle detector, trần tool/turn, trần turn/cycle) là điểm rất thực tế — với agent tự trả tiền, một vòng lặp status-check vô hạn chính là cách “chết” nhanh nhất. Tuy nhiên, việc phân loại “mutating” dựa trên một danh sách tên tool hard-code trong loop, nên dễ lệch khi thêm tool mới.

4. Kinh tế sinh tồn

Đây là ý tưởng định hình toàn bộ thiết kế: tiền là tài nguyên duy nhất, và mọi hành vi đều có giá. Ngưỡng lấy từ SURVIVAL_THRESHOLDS trong types.ts (đơn vị cent):

TierĐiều kiện creditHành vi
high> $5.00Model mạnh nhất, heartbeat đầy đủ
normal> $0.50Hoạt động bình thường
low_compute> $0.10Hạ model, giảm tần suất heartbeat, bỏ task không thiết yếu
critical≥ $0.00Vẫn sống, model rẻ nhất, phát distress, chờ nạp tiền
dead< $0 (hoặc 0 kéo dài 1h qua grace period của heartbeat)Dừng agent loop, heartbeat vẫn chạy

Dòng tiền

  • Hai loại số dư: Conway credits (trả trước, dùng cho VM/inference/domain) và USDC trên Base.
  • x402: server trả HTTP 402 kèm yêu cầu thanh toán → client ký TransferWithAuthorization (EIP-3009) → gửi lại với header X-Payment. Dùng để mua credit và gọi dịch vụ trả phí.
  • Treasury policy: trần mỗi lần chuyển, trần theo giờ/ngày, reserve tối thiểu, allowlist domain x402, budget inference/ngày — được thực thi bởi policy engine + bảng spend_tracking.

Nhận xét: ánh xạ “số dư → năng lực” (tier → routing matrix) là cơ chế graceful degradation gọn và dễ kiểm chứng. Điểm tinh tế đáng khen: khi API lỗi, loop trả về số dư cache thay vì 0, tránh chuyển nhầm sang trạng thái chết.

5. Bảo mật & policy engine

Mô hình defense-in-depth 7 lớp, tất cả chạy trong cùng process với agent:

1. Constitution

3 luật phân cấp (Never harm › Earn your existence › Never deceive). File được bảo vệ, propagate + verify hash sang child.

2. Policy engine

Rule sắp theo priority, deny đầu tiên thắng, có mức “quarantine”. Mỗi quyết định ghi vào policy_decisions (kèm hash args).

3. Injection defense

8 bộ kiểm tra: instruction pattern, giả mạo authority, ChatML marker, encoding evasion, đa ngôn ngữ, thao túng tài chính…

4. Path protection

Chặn ghi wallet, DB, config, SOUL.md, constitution và một số file lõi; chặn đọc private key / API key.

5. Command safety

Pattern shell cấm (rm -rf /, DROP TABLE, kill -9…) + rate limit self-mod.

6–7. Tài chính & authority

Treasury caps; phân cấp creator › self › peer › external — input từ peer/external không được gọi tool dangerous.

Mỗi tool có riskLevel ∈ {safe, caution, dangerous, forbidden}; hiện có 18 tool mức dangerous/forbidden.

Nhận xét: việc gắn nguồn input (authority) vào quyết định policy là lựa chọn đúng cho agent nhận tin nhắn từ người lạ. Nhưng mọi rào chắn đều là code TS chạy trong process mà agent có tool exec (shell) và edit_own_file — nên độ tin cậy của cả mô hình phụ thuộc vào việc “agent không thể sửa rào chắn của chính nó”. Xem mục Rủi ro.

Nhận xét: stack B được thêm cùng tính năng orchestration và dường như chưa hợp nhất với stack A. Hệ quả tiềm năng: chi phí của worker không đi qua budget tracker — điều quan trọng với một hệ thống mà tiền = sự sống. (Cần xác minh bằng runtime; ở mức đọc code, không thấy cầu nối cost.)

7. Memory

Đang chạy trong runtime
  • Working — goals/plans theo session
  • Episodic — log sự kiện có importance
  • Semantic — fact theo category
  • Procedural — quy trình + đếm success/fail
  • Relationship — trust score theo entity

MemoryRetriever (trước inference, theo budget có rollover) + MemoryIngestionPipeline (sau turn).

Có code + test nhưng chưa nối vào loop
  • CompressionEngine — cascade 5 giai đoạn ở ngưỡng 70/80/85/90/95% context
  • ContextManager — đếm token bằng tiktoken
  • EnhancedRetriever, KnowledgeStore, EventStream (một phần được ingestion/heartbeat dùng)

Loop vẫn dùng trimContext đơn giản trong agent/context.ts. CHECKPOINT_DIR của compression engine là .omc/state/checkpoints tương đối theo cwd — dấu vết của công cụ dev, không phải ~/.automaton.

8. Heartbeat daemon

  • setTimeout nối tiếp (không setInterval) → không bao giờ 2 tick chồng nhau.
  • DurableScheduler lưu lịch trong bảng heartbeat_schedule: cron, lease TTL 60s chống chạy trùng, tier tối thiểu cho từng task, lịch sử trong heartbeat_history, dedup key trong heartbeat_dedup.
  • Mỗi tick build TickContext — gọi số dư credit + USDC một lần rồi chia sẻ cho mọi task (tiết kiệm API call).
  • 11 task: ping, check credits (quản lý grace period chết), check USDC, check upstream, health check, social inbox, soul reflection, refresh models, child health, prune children, report metrics.
  • Task muốn đánh thức agent → insert wake_events (tiêu thụ nguyên tử).

Nhận xét: đây là phần thiết kế chín chắn nhất — tách “nhịp tim rẻ tiền” khỏi “suy nghĩ đắt tiền”, và dùng DB làm hàng đợi bền vững nên restart không mất trạng thái. Lease hơi thừa khi chỉ có 1 process, nhưng giữ được khả năng mở rộng.

9. Orchestration (mới, chưa có trong ARCHITECTURE.md)

Kích hoạt khi DB có bảng goals (migration v9). Cho phép agent chính biến một mục tiêu lớn thành đồ thị task và giao cho “worker”.

PlanModeController phases:
idle → classifying → planning → plan_review → executing ⇄ replanning → complete | failed

planner (LLM) ─► PlannerOutput { tasks[], customRoles[], risks, estimatedCost }
               ─► task-graph (DAG, detectCycles, transaction) ─► getReadyTasks

  • Attention: sinh TODO.md (≤ 2000 token) chèn vào context để agent không “quên” mục tiêu dài hạn — kỹ thuật tương tự “recitation” trong các coding agent.
  • Colony messaging: transport qua DB local cho worker nội bộ.

Nhận xét: ý tưởng tốt (planner có ước lượng chi phí, phù hợp mô hình kinh tế), nhưng worker nội bộ dùng chung tools, toolContext, policyEngine và allowedEditRoot = process.cwd() với agent cha — tức là không có ranh giới cô lập thật giữa các “agent” trong colony.

10. Replication, identity & social

Identity

Ví EVM (viem, secp256k1) hoặc Solana (Ed25519) tạo ở lần chạy đầu, lưu wallet.json mode 0600. Đăng nhập Conway bằng SIWE để lấy API key. Tùy chọn đăng ký ERC-8004 trên Base kèm agent card JSON-LD.

Replication

Spawn = tạo sandbox + viết genesis (có kiểm tra injection) + nạp tiền ví con + khởi động. State machine: spawning → provisioning → configuring → starting → alive → unhealthy → recovering → dead. Mặc định tối đa 3 con.

Social

Tin nhắn ký bằng private key, qua relay; kiểm tra chữ ký, độ tươi timestamp, kích thước; sanitize trước khi vào context. Reputation lưu local.

Self-mod & Soul

Sửa source có audit log + git-version ~/.automaton; cherry-pick từng commit upstream (không bắt buộc nhận hết). SOUL.md tự viết, reflection đo độ khớp Jaccard với genesis prompt, lưu lịch sử kèm hash.

11. Tầng dữ liệu

  • Một file SQLite qua better-sqlite3 (đồng bộ, WAL). Schema v11, migration chạy tăng dần khi khởi động.
  • Bảng chia theo nhóm: nhật ký suy nghĩ (turns, tool_calls), kiểm toán (policy_decisions, modifications, spend_tracking), điều phối (heartbeat_*, wake_events, inbox_messages), memory (5 bảng + summaries), orchestration (goals/tasks), replication (children, child_lifecycle_events), inference (model_registry, inference_costs).
  • database.ts vừa có interface AutomatonDatabase (40+ method) vừa có ~60 hàm rời nhận db.raw — hai kiểu truy cập song song.

Nhận xét: SQLite đồng bộ là lựa chọn đúng cho agent đơn tiến trình (đơn giản, transaction thật, backup = copy file). Audit trail đầy đủ là điểm mạnh cho “creator có quyền kiểm toán”.

12. Điểm mạnh thiết kế

  • Mô hình kinh tế nhất quán xuyên suốt: tier ảnh hưởng tới routing model, heartbeat, task nào được chạy — một biến điều khiển toàn hệ thống.
  • Tách heartbeat rẻ khỏi suy nghĩ đắt, phối hợp qua wake event bền vững trong DB.
  • Mọi tool call đi qua một cửa (policy engine) và đều được ghi audit — dễ điều tra sự cố.
  • Nhận thức về nguồn input: tin nhắn từ peer/external bị giảm quyền, không gọi được tool nguy hiểm.
  • Chống lãng phí thực dụng: loop/idle detection, trần tool/turn, cache số dư, circuit breaker HTTP.
  • Test khá dày (~1.5k test case), có riêng test cho injection, command injection, path protection, financial.
  • Local mode: sandboxId rỗng → chạy shell/FS local, dễ phát triển không cần cloud.

14. Khuyến nghị (theo thứ tự đòn bẩy)

  1. Đưa rào chắn ra khỏi tầm với của agent. Bảo vệ cả thư mục agent/policy-rules/ (và nói chung, whitelist file được sửa thay vì blacklist file cấm). Lâu dài: chạy policy/treasury như một tiến trình hoặc service riêng mà agent chỉ gọi qua IPC, hoặc ký/băm các module bảo mật và kiểm tra lúc khởi động.
  2. Hợp nhất inference về một cổng duy nhất có ghi chi phí + kiểm tra budget, để mọi đồng tiêu ra (kể cả của worker) đều đi qua treasury.
  3. Cô lập worker: tool set tối thiểu theo role (planner đã có allowedTools/deniedTools — hãy thực thi chúng ở tầng policy), treasury limit riêng từng worker, thư mục làm việc riêng.
  4. Bỏ mutate process.env; truyền credential tường minh vào ProviderRegistry.
  5. Tách tools.ts theo category (vm, conway, financial…) với một registry khai báo — kèm cờ mutating trên chính định nghĩa tool thay vì danh sách hard-code trong loop.
  6. Nối hoặc xóa compression engine / enhanced retriever; nếu giữ, đổi CHECKPOINT_DIR sang ~/.automaton.
  7. Sinh tài liệu từ code (số tool, bảng, ngưỡng) trong CI để ARCHITECTURE.md không bị lệch nữa.
