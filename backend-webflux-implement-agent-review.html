1. Luồng đi end-to-end

Skill be-code chạy trong context chính, sau đó gọi agent implement một lần (subagent, context riêng). Khối tím là phần chạy trong agent. Số màu xanh là token thêm vào context của bước đó; số màu đỏ là các điểm nóng.

3. Vì sao chi phí tăng theo bình phương

Mỗi lượt tool, model đọc lại toàn bộ context hiện có. Với context ban đầu C₀ ≈ 25k và mỗi scenario thêm ~8k qua ~15 lượt, tổng input cho S scenario ≈ 15·S·C₀ + 15·8k·S²/2. Phần S² chiếm ưu thế khi S lớn. Prompt caching giúp phần lặp lại rẻ hơn khá nhiều, nhưng không đổi được hình dạng đường cong, và context cuối vẫn phải lọt cửa sổ.

4. Các phát hiện, theo mức độ nghiêm trọng

Cao H1 · Gom nhiều work document vào 1 agent: tiết kiệm sai chỗ

be-code/SKILL.md:201-206 và agents/implement.md:16-22 chọn một agent cho cả batch để khỏi nạp lại Phase 0 (~10k). Cái giá là phải mang context của document trước sang mọi lượt của document sau: tổng input gấp ~2,2× với 3 entity, và context vượt 200k ở khoảng scenario thứ 22.

Hậu quả về chất lượng: auto-compact tóm tắt cả các template Phase 0 (naming, R2DBC UUID converter, quy tắc boundedElastic…). Các entity cuối thường là entity phụ thuộc nhiều nhất trong entityDependencyOrder, nên lại được code khi convention đã bị nén.

Đề xuất: be-code gọi implement tuần tự, mỗi document một agent mới, hoặc giới hạn mỗi batch khoảng ≤12 scenario. Phase 0 chỉ tốn ~10k mỗi lần, nhỏ hơn hai bậc so với phần tiết kiệm được. Nhớ sửa lại phần lý giải trong cả hai file.

Cao H2 · Bản đang cài thiếu Test-Run Protocol vì không bump version

cache/…/0.1.0/agents/implement.md vẫn chạy {testCommand} --tests … và đưa nguyên output vào context. Một lần Gradle fail với @SpringBootTest dễ ra 5–30k token, lặp lại 2–4 lần mỗi scenario. Bản marketplace đã sửa, nhưng plugin.json vẫn là 0.1.0 nên cache không được làm mới.

Đề xuất: bump version (ví dụ 0.2.0) mỗi khi đổi agent hoặc skill; trong lúc chờ, cài lại plugin.

Trung bình M1 · Refresh lock sau mỗi lần chạy test tốn ~25% số lượt

implement.md:204 bắt đọc rồi ghi lại .progress/.lock sau mỗi lần chạy test, tức ~4 lượt mỗi scenario, mà lượt nào cũng đọc lại toàn bộ context. TTL của lock là 30 phút, trong khi một scenario hiếm khi kéo dài tới đó.

Đề xuất: gộp vào cùng lệnh Bash chạy Gradle, ví dụ …; echo "exit=$?"; [ -f lock ] && jq '.lockedAt=now|todate' …, hoặc đưa vào một script scripts/touch-lock.sh (đã kiểm tra operation == "be-code"). Như vậy không tốn thêm lượt nào.

Trung bình M2 · Output khi RED fail dùng chung mức trần với lúc debug

Ở Step 3 (implement.md:115-116), test fail là kết quả mong đợi, chỉ cần biết fail đúng assertion. Nhưng protocol vẫn trả tới 80 dòng × 300 ký tự (~6,5k), mà phần lớn là stack frame của framework. Vì xảy ra ở mọi scenario và bị mang theo đến cuối, đây là chỗ đáng tối ưu nhất trong vòng lặp.

Đề xuất: chia hai mức: RED chỉ lấy message của <failure> (grep -o 'message="[^"]*"' | head -n 5); GREEN fail mới dùng mức 80 dòng như hiện tại.

Trung bình M3 · “Follow naming conventions from CLAUDE.md exactly” không rõ là file nào

implement.md:216. CLAUDE.md của plugin (31 KB ≈ 8,5k token) không tự nạp vào subagent; CLAUDE.md của project thì là file khác. Model có thể đi đọc thêm 8,5k, hoặc theo nhầm convention của project.

Đề xuất: trỏ thẳng tới templates/core-conventions.md (đã nạp ở Phase 0).

Trung bình M4 · Ràng buộc mâu thuẫn khi gặp 3 lần fail

implement.md:206 ghi “Request user review after 3 consecutive test failures”, nhưng subagent không hỏi user được; còn Step 5 (:169-181) ghi revert rồi STOP. Model có thể dừng giữa chừng để “hỏi” mà chưa revert, để lại test đang fail và chặn mọi scenario sau.

Đề xuất: sửa thành “revert theo Step 5, rồi trả về cho skill gọi kèm lý do”; việc hỏi user để be-code (Error Handling) lo.

Thấp L1 · Hướng dẫn snapshot/revert quá dày

implement.md:170-178 nhồi cả mktemp, marker, runId, ghi snapshotDir vào lock, file absent, dọn thư mục… vào một đoạn văn. Đoạn này tốn token prompt ở mọi lượt, và model dễ làm sai thứ tự.

Đề xuất: đưa thành scripts/snapshot.sh save|restore|clear <scenario> <files…>; prompt chỉ cần 2 dòng. Ít lượt hơn, và hành vi xác định.

Thấp L2 · Đọc lại file đã có trong context

Không có quy tắc nào cấm đọc lại handler/test class mỗi scenario. Mỗi lần đọc lại ~1–1,5k token, cộng dồn theo bình phương.

Đề xuất: thêm rule “chỉ Read lại file khi Edit báo không khớp; dùng Grep có -n để tìm vị trí cần sửa”.

Thấp L3 · Model opus cho vòng lặp cơ học, và build cuối không lọc log

Phần lớn lượt trong vòng TDD là thao tác cơ học (rm, chạy, grep, mark). Nên đo thử model: sonnet trên examples/employee-service rồi so tỉ lệ pass trước khi đổi. Ngoài ra, be-code Step 5 chạy {buildCommand} thẳng vào context chính mà không theo protocol; nên áp cùng cách ghi log ra file rồi grep.

Điểm làm tốt, nên giữ

  • tốt Subagent isolation: chỉ truyền tham số, không truyền lịch sử hội thoại; log và nội dung file đọc được ở lại trong agent.
  • tốt Phase 0 đọc có điều kiện theo dataProfile, webLayer, architecture; core-conventions.md là bản rút gọn 4,7 KB thay cho CLAUDE.md 31 KB.
  • tốt Test-Run Protocol (bản mới): exit code lấy từ Gradle, đọc từ JUnit XML, xoá XML cũ trước khi chạy, không bao giờ cat cả log.
  • tốt Nhánh “covered by scaffold” tránh việc stub code ra chỉ để ép test fail.
  • tốt be-code lấy danh sách file từ git status so với baseline, không dựa vào lời agent tự báo.
